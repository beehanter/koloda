# Журнал отладки скриптов запуска и остановки (19.10.2025)

Этот документ описывает процесс отладки скриптов `start.bat` и `stop.bat` для корректного запуска и, что более важно, остановки фоновых сервисов (Streamlit, Static Server) в среде Windows.

## 1. Исходная проблема

При запуске `start.bat` сервисы запускались, но `stop.bat` не мог их остановить. Процессы Streamlit и другие оставались висеть в системе ("зомби-процессы"). Это приводило к проблемам, таким как смена порта Streamlit при перезапуске (с 8501 на 8502), что указывало на то, что старый процесс не был завершен.

## 2. Процесс отладки: Попытки и выводы

Мы прошли через несколько итераций, каждая из которых выявляла новый, более глубокий слой проблемы.

### Попытка №1: Запуск в отдельных окнах и остановка по заголовку

-   **Идея:** Запускать каждый сервис в отдельном окне CMD с уникальным заголовком (`start "StreamlitApp" ...`) и останавливать его с помощью `taskkill`, ища процесс по этому заголовку (`taskkill /FI "WINDOWTITLE eq StreamlitApp"`).
-   **Проблема:** `taskkill` не находил окна. Мы предположили, что заголовок либо не присваивается дочернему процессу `python.exe`, либо переименовывается самим Streamlit.

### Попытка №2: Использование PID-файлов

-   **Идея:** Перейти к промышленному подходу. При запуске каждого процесса получать его уникальный **Process ID (PID)** и сохранять в файл (например, `.pids/streamlit.pid`). Скрипт `stop.bat` должен был читать PID из файла и целенаправленно завершать процесс по его ID (`taskkill /PID ...`).
-   **Проблема:** Процессы перестали запускаться вообще. Мы выяснили, что низкоуровневый инструмент `wmic process call create`, который мы использовали для получения PID, запускает процессы в "чистом" системном окружении, без доступа к виртуальному окружению Python (`.venv`) и без правильной рабочей директории. Процессы молча падали, не находя нужные файлы или библиотеки.

### Попытка №3: Улучшение PID-подхода

-   **Идея:** Исправить проблему `wmic`, передавая ему полные, но динамические пути к `python.exe`, `uv.exe` и скриптам, а также явно указывая рабочую директорию.
-   **Проблема:** Это сделало скрипты чрезвычайно сложными и все равно приводило к сбоям запуска ("зависанию"), так как `start /B` некорректно работал с консольными приложениями, ожидая их завершения.

## 3. Финальное и рабочее решение (предложено пользователем)

В итоге мы вернулись к самой первой, простой идее, но усовершенствовали метод остановки.

**`start.bat` (финальная версия):**
Простой и надежный запуск каждого сервиса в отдельном окне с установкой точного заголовка.
```batch
@echo off
ECHO "Starting the application..."
...
ECHO " - Starting Streamlit..."
start "StreamlitApp" cmd /c "title StreamlitApp && uv run python -m streamlit run stream/app.py"
...
```

**`stop.bat` (финальная, рабочая версия):**
Вместо ненадежного `taskkill` используется мощная команда **PowerShell**, которая находит все процессы, чей заголовок окна *соответствует* одному из шаблонов, и надежно их завершает.

```batch
@echo off
ECHO "Stopping all application processes..."
...
ECHO "Stopping service windows..."
powershell -Command "Get-Process | Where-Object { $_.MainWindowTitle -match 'DataProcessing|StaticServer|StreamlitApp' } | Stop-Process -Force"
...
```

### Ключевые выводы

1.  Простой подход часто является самым надежным. Запуск сервисов в отдельных видимых окнах — это наглядно и предсказуемо.
2.  Стандартный `taskkill` в `cmd.exe` имеет много ограничений и может быть ненадежен при поиске по заголовкам окон.
3.  **PowerShell** является гораздо более мощным и гибким инструментом для автоматизации и управления процессами в Windows. Его команда `Get-Process | Where-Object | Stop-Process` — это промышленный стандарт для решения подобных задач.

Это решение является одновременно простым, читаемым и чрезвычайно надежным.
